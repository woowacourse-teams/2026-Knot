# 현재 V2 MVP 기획 기준

이 문서는 기획·구현·리뷰에서 현재 작업에 적용할 원문을 찾는 진입점이다.
제품 정책 전문은 Notion 원문에서 관리한다. 이 문서의 범위 요약이나 과거 구현을
새로운 제품 결정의 근거로 사용하지 않는다.

- 관련 작업: [#374](https://github.com/woowacourse-teams/2026-Knot/issues/374)
- 자료 확인: 2026-10-01, 운영 Team Notion 로그인 브라우저와 n8n Data Table을 다시 확인
- 원문 시점: 도메인 규칙은 운영 Notion에서 확인. API 세부 후보는 2026-09-30 07:16 UTC
  (16:16 KST)에 감지된 n8n 대기 항목 기준
- n8n 관측: 2026-10-01 11:37 KST, `knot_notion_sources` 741행, `knot_notion_pending` 37행.
  로그인 관련 API 후보 4건은 모두 `pending`, claim·lease 비어 있음
- 상태 주의: API 세부 후보는 대기열에 남아 있으며 팀의 최종 승인이나 구현 완료를
  뜻하지 않는다. 최신 수집 상태와 검토 절차는 [Notion 정합성 워크플로](../harness/notion-alignment.md)를 따른다.

## 작업 시작 순서

1. 현재 사용자 지시와 연결된 Issue의 범위를 확인한다. 사용자 지시로 정한 범위가
   팀 문서와 다르면 작업에 적용한 지시와 팀 문서에 남은 충돌을 구분해 기록한다.
2. 아래 출처표에서 해당 도메인의 원문과 변경 로그를 읽는다. 문서 제목의 `V2`,
   `최종`, `확정` 또는 수정 시각만으로 적용 여부를 결정하지 않는다.
3. 해당 항목이 현재 MVP에 포함되는지, 이전 결정을 명시적으로 대체했는지,
   충돌 목록에 남아 있는지 확인한다. Issue에 근거 문서·항목·확인 날짜를 남긴다.
4. 같은 항목의 출처가 충돌하거나 접근할 수 없으면 그 판단을 보류하고 영향 범위와
   확인할 질문을 적는다. [Notion 정합성 워크플로](../harness/notion-alignment.md)에 따라
   Notion 주장, 저장소 문서, Issue와 실제 코드를 나란히 제시해 사용자 결정을 받는다.
   과거 문서나 AI 추론으로 빈 정책을 채우지 않는다. 확정 근거가 있는 독립 작업은 계속한다.
5. 제품 범위 확인 후 기존 API 계약·ADR·백엔드 컨벤션을 함께 적용한다.
   제품 기획의 빈 항목만으로 이미 있는 구현 계약을 폐기하지 않는다.

## 왜 현재 범위를 구분하는가

V1의 Notion 수집·검색 구현과 초기 V2의 공동 녹음·동시 편집 기획이 자료에 함께 남아 있다.
[변경 로그]의 2026-09-22 항목은 현재 V2가
녹음 → STT 전사 → 요약·문서 아카이빙 → 탐색에 집중하도록 범위를 줄였다고 설명한다.
공동 녹음과 여러 세션에 참여하는 흐름은 이후 버전으로 이동했다.
2026-09-23 항목은 도메인 규칙을 이 범위에 맞추면서 남은 충돌도 별도로 표시했다.

[#372](https://github.com/woowacourse-teams/2026-Knot/issues/372)는 V1 채팅·검색·Notion
구현 제거 작업이다. 제거 사실은 V2 대체 기능이 구현됐다는 뜻이 아니다.
인증·회원·워크스페이스·멤버십·초대와 공통 기반은 유지 대상으로 구분됐다.

수정 시각, 본문에 적힌 `확정` 표현만으로 채택 여부를 판단하지 않는다. 원문에 접근할 수
없거나 다른 현재 문서와 충돌하면 결론을 보류하고 정합성 워크플로에 따라 질문한다.

## 현재 MVP 범위 요약

다음은 [도메인 규칙]과 [변경 로그]에서 확인되는 범위다. 상세 조건은 원문을 따른다.

| 항목 | 현재 범위 | 이전 기획과 구분 |
| --- | --- | --- |
| Member·로그인 | GitHub OAuth 가입·로그인, GitHub 계정 하나당 Member 하나, 로그인 → 닉네임 입력 → 가입 완료. 닉네임은 최대 20자이며 한글·영어·`( ) -` 허용, 공백 불가. GitHub 프로필 이미지를 기본값으로 사용하고 Member는 여러 Workspace에 참여 가능 | 서버도 같은 닉네임 규칙으로 검증. OAuth 세션·토큰 갱신·만료와 가입 중단 재진입은 미정이며, 계정 삭제 후 재로그인 제한은 API 후보에서만 제안 |
| Workspace 수명 | 생성 개수 제한 없음. OWNER는 OWNER 권한을 다른 멤버에게 넘기거나 Workspace를 삭제한 뒤 나갈 수 있으며, 마지막 멤버가 나가면 soft-delete | 이전의 생성 3개 제한 및 OWNER가 승계 없이 나갈 수 있다는 규칙을 현재 도메인 원문이 대체 |
| 녹음 | 시작한 Member 단독 진행, Member당 진행 중 녹음 1개, 일시정지·종료 | 다른 Member의 참여, 공동 녹음, 녹음 중 메모는 현재 범위 밖 |
| 녹음 상한 | 2시간, 종료 15분 전 안내 | 9/23에 시간 제한 없음·3시간·4시간 제안을 대체 |
| 문서 정리 | 전사 후 주제별 문서 생성, 홈에서 정리 중·실패 상태 확인 | 녹음 종료가 곧 문서 생성 완료라는 의미는 아님 |
| 문서 | 읽기·원문 조회·복사·멤버별 확인 | Document의 DRAFT·ARCHIVED 상태 없음. 편집·삭제·직접 작성·가져오기 제외 |
| 탐색 | Workspace·Member별 개인 대화와 사용한 문서 근거 | 기존 V1 검색·채팅 코드의 제거와 V2 기획 범위를 혼동하지 않음 |
| 접근 | 현재 Workspace 멤버십으로 녹음·문서·탐색 접근 검사 | 녹음 참여 여부를 문서 읽기 권한으로 사용하지 않음 |

이전 V2의 공동 녹음·동시 편집·다중 세션 화면이 남아 있어도 현재 범위로 되돌리지 않는다.
Member당 1개라는 규칙만으로 Workspace 전체 상한을 추론하지 않는다. 최종 ERD는
Workspace 전체 상한이 없다고 적지만, 도메인 규칙은 A2 경고를 남겨 두었다. 동시에 다른
멤버가 녹음할 수 있는지와 전체 상한은 저장소 작업에서 별도 결정을 받기 전까지 충돌로
취급한다.

### 인증·로그인 정합 상태

`(신)도메인`은 GitHub OAuth, GitHub 계정당 Member 하나, 닉네임 입력 뒤 가입 완료,
닉네임 규칙, 기본 GitHub 프로필 이미지와 여러 Workspace 참여를 현재 도메인으로 적는다.
현재 `아직 정하지 않은 것` 페이지는 OAuth 세션·토큰 갱신·만료와 가입 중단 후 재진입을
미정으로 적는다. 이 스레드에 제공된 도메인 발췌에는 중복 요청 멱등성과 닉네임 중복·변경
정책도 미정으로 있었지만, 현재 확인한 해당 Notion 페이지에는 그 두 항목이 보이지 않는다.
누락이 결정인지 단순 정리 차이인지 확인 전까지 미정으로 취급한다.

2026-09-30 캡처에는 GitHub OAuth callback, 닉네임 설정, refresh, logout API 후보가 있다.
모두 n8n 대기열에서 `pending`이고 미승인 초안이다. 후보 흐름과 현재 코드의 차이, Notion
브라우저 본문과 n8n refresh snapshot 사이의 내용 차이는
[백엔드 로그인·API 정합 메모](../../backend/docs/notion-api-alignment.md#인증로그인-2026-09-30-후보)에,
저장·동시성 제안과 미정 결정은
[Persona 로그인 세션 draft](../../backend/.persona/decisions/draft/refresh-token-session-lifecycle.md)에
기록했다. 승인된 제품 기준이나 FE 동작으로 옮기기 전에는 후보 상태와 원문 정합을 다시
확인한다.

OAuth 후보의 탈퇴 Member 재로그인 제한도 도메인 확정 사항은 아님 | 중복 요청·닉네임 중복/변경과 가입 재진입, refresh 동시 요청·저장 방식·실패 cookie 처리·탈퇴/정지 시 폐기 범위를 원문 및 팀 승인으로 정리한 뒤 Issue에 연결 |

| 최종 오디오 업로드 | 9/23 이후 도메인 규칙과 9/30 API 후보는 종료 후 최종 파일 1개 업로드를 설명하고, 9/22 ERD에는 chunk 업로드 구조가 남아 있음 | 구현 전 제품 흐름과 DB 모델의 저장 단위를 맞추고, 불필요한 chunk 모델을 둘지 결정 |

이미 사용자가 확정한 후속 Issue의 결정이 있다면 같은 질문을 다시 하기 전에
그 결정의 대상·적용 범위·근거를 확인한다. 대화에서 채택한 내용을 팀 승인으로
표현하지 말고, 팀이 조회할 수 있는 Issue·PR에 기록해 원문과의 차이를 추적한다.

### #374 구현 중 확인한 담당자 결정

다음은 2026-09-29 #374 작업 대화에서 확인한 녹음 담당자의 지시다.
팀 Notion에 반영됐거나 팀 리뷰가 승인했다는 의미는 아니다.

- 연결 끊김은 이전 대화의 30초 heartbeat·2분 유예를 확정 기준으로 옮기지 않고,
  원문의 즉시 종료와의 충돌을 남겨 녹음 구현 전에 확정한다.
- 같은 멤버의 다른 탭·기기는 상태와 경과 시간을 보고 종료할 수 있다.
  새 녹음은 막고, 오디오 수집과 일시정지는 처음 녹음을 시작한 탭이 맡는다.
  이는 다른 멤버의 공동 녹음 참여와 별개다.
- 녹음 탭을 새로고침·닫을 때 브라우저 기본 나가기 확인을 거쳐 나가면 종료 신호를
  보내고 거기까지 문서로 정리한다. 다시 들어오면 문서 정리 중 상태이며 이어 녹음은
  이후 버전이다. 종료 신호가 전달되지 않은 경우의 처리 시점은 연결 끊김 결정과 함께 확인한다.

이 결정의 후속 녹음 Issue를 등록하면 해당 링크와 원문 동기화 상태를 갱신한다.

## 계속 적용할 기존 규칙

V2 전환은 모든 기술 규칙과 ADR의 일괄 폐기가 아니다.

- [기여 가이드](../../CONTRIBUTING.md), [GitHub 컨벤션](../../.github/knot-conventions.yml),
  기존 Issue·PR 템플릿과 [Issue·ADR 하네스](../harness/issue-planning.md)는 계속 적용한다.
- 인증·초대·워크스페이스 계약은 관련 [ADR 목록](../adr/README.md), 연결 Issue,
  실제 API·테스트를 확인한다. 새 기획에 없다는 이유만으로 기존 계약을 제거하지 않는다.
  명시적 충돌이 발견되면 영향과 대체 결정을 해당 작업에서 다룬다.
- 백엔드의 팀 컨벤션은 [백엔드 컨벤션 원문][백엔드]의 00~08 개별 문서를 읽는다.
  V2 제품 범위와 언어·계층·테스트·API 작성 규칙은 별도로 판정한다.
- 과거 Notion 수집·검색 ADR은 당시 결정의 이력으로 보존한다. V2 요구사항으로
  자동 재사용하지 않는다. 실제 설계를 대체할 때 [ADR 생명주기](../adr/README.md)에
  따라 새 결정과 대체 관계를 남긴다.

## 변경 시 갱신

정책을 바꾸는 작업에서는 원문의 해당 항목과 변경 로그를 먼저 확인하고,
이 문서의 관련 범위·충돌 상태·확인 날짜·출처를 함께 갱신한다.
결정 전 제안은 미정으로 남기고, 해소했다면 결정한 Issue 또는 PR을 연결한다.
원문 동기화가 남아 있으면 대상 문서와 남은 차이를 표시한다.

AGENTS에는 이 문서로 향하는 진입점만 유지한다. 개인 로컬 스킬의 출처 우선순위와
위키 라우팅 보완은 #374 저장소 PR 밖의 후속 작업이며, 개인 스킬을 저장소에 복사하지 않는다.
제품 코드, 하네스 판정 로직, 기존 ADR 전체 개편은 이 문서 정리의 범위가 아니다.
