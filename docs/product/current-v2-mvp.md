# 현재 V2 MVP 기획 기준

이 문서는 기획·구현·리뷰에서 현재 작업에 적용할 원문을 찾는 진입점이다.
제품 정책 전문은 Notion 원문에서 관리한다. 이 문서의 범위 요약이나 과거 구현을
새로운 제품 결정의 근거로 사용하지 않는다.

- 관련 작업: [#374](https://github.com/woowacourse-teams/2026-Knot/issues/374)
- 자료 확인: 2026-10-01, 운영 Team Notion·n8n Data Table·GitHub Issue 확인
- 원문 시점: 도메인 규칙은 운영 Notion에서 확인. API 세부 후보는 2026-09-30 07:16 UTC
  (16:16 KST)에 감지된 n8n 대기 항목 기준
- n8n 관측: 10/1 14:32 KST에는 741 source와 37 queue row가 모두 `pending`이었다. 15:00
  KST 재확인에서는 14개가 `processed`, 23개가 `pending`, `verified`는 0개였다. 마지막
  `captured_at`은 9/30 16:16 KST다. `Knot Notion Change Queue` 편집기는 15:00에도
  `Publish`를 표시해 미게시 상태였고, 새 capture는 확인되지 않았다. 별도
  `Knot Notion Queue Completion`은 게시된 5분 예약 workflow이며 최신 화면에서 성공 상태였다.
  15:24 KST 수동 capture는 `Get many child blocks`의 429 rate limit 오류로 멈췄고 upsert 전이라
  Data Table은 갱신되지 않았다. 처리 대상과 row별 근거는 [정합성 워크플로](../harness/notion-alignment.md)
  checkpoint에 둔다.
- 상태 주의: API 세부 후보는 대기열에 남아 있으며 팀의 최종 승인이나 구현 완료를
  뜻하지 않는다. 최신 수집 상태와 검토 절차는 [Notion 정합성 워크플로](../harness/notion-alignment.md)를 따른다.

## 작업 시작 순서

1. 현재 사용자 지시와 연결된 Issue의 범위를 확인한다. 사용자 지시로 정한 범위가
   팀 문서와 다르면 작업에 적용한 지시와 팀 문서에 남은 충돌을 구분해 기록한다.
2. 아래 출처표에서 해당 도메인의 원문과 변경 로그를 읽는다. 문서 제목의 `V2`,
   `최종`, `확정` 또는 수정 시각만으로 적용 여부를 결정하지 않는다.
3. 해당 항목이 현재 MVP에 포함되는지, 이전 결정을 명시적으로 대체했는지,
   충돌 목록에 남아 있는지 확인한다. Issue에 근거 문서·항목·확인 날짜를 남긴다.
4. 같은 항목의 출처가 충돌하거나 접근할 수 없으면 그 판단을 보류하고 영향 범위와
   확인할 질문을 적는다. [Notion 정합성 워크플로](../harness/notion-alignment.md)에 따라
   Notion 주장, 저장소 문서, Issue와 실제 코드를 나란히 제시해 사용자 결정을 받는다.
   과거 문서나 AI 추론으로 빈 정책을 채우지 않는다. 확정 근거가 있는 독립 작업은 계속한다.
5. 제품 범위 확인 후 기존 API 계약·ADR·백엔드 컨벤션을 함께 적용한다.
   제품 기획의 빈 항목만으로 이미 있는 구현 계약을 폐기하지 않는다.

## 왜 현재 범위를 구분하는가

V1의 Notion 수집·검색 구현과 초기 V2의 공동 녹음·동시 편집 기획이 자료에 함께 남아 있다.
[변경 로그]의 2026-09-22 항목은 현재 V2가
녹음 → STT 전사 → 요약·문서 아카이빙 → 탐색에 집중하도록 범위를 줄였다고 설명한다.
공동 녹음과 여러 세션에 참여하는 흐름은 이후 버전으로 이동했다.
2026-09-23 항목은 도메인 규칙을 이 범위에 맞추면서 남은 충돌도 별도로 표시했다.

[#372](https://github.com/woowacourse-teams/2026-Knot/issues/372)는 V1 채팅·검색·Notion
구현 제거 작업이다. 제거 사실은 V2 대체 기능이 구현됐다는 뜻이 아니다.
인증·회원·워크스페이스·멤버십·초대와 공통 기반은 유지 대상으로 구분됐다.

## 현재 MVP 범위 요약

### 2026-10-03 초대 최소 MVP

사용자가 확정한 [#399](https://github.com/woowacourse-teams/2026-Knot/issues/399)는
한 초대의 코드·링크를 함께 생성하고 공통 `expiresAt`에 함께 만료한다. 복수 초대와 다수 수락을 허용하고,
새 발급은 기존 초대를 무효화하지 않는다. 취소·연장·복원·발급자별 관리는 제외한다.
신규 코드는 A-Z 6자리이며 초대는 생성 24시간 뒤 만료한다.
사용자가 2026-10-03 #443 검토 중 공통 만료를 채택했으며 앞선 독립 만료 결정을 대체한다.

기존 유효·만료·무효 초대의 효력을 보존한다. 구 재발급·원문 재조회와 FE 숫자 코드
호환을 전환하기 전에는 복수 발급을 공개하지 않는다. #439는 공통 만료·기존 데이터 보존과
FK RESTRICT를 검증하며 공개 API 전환 완료를 뜻하지 않는다. 삭제 Workspace 접근 차단은 유지한다.
상세 결정은 [Proposed ADR](../adr/399-workspace-invitation-expiry-only-mvp.md)을 따른다.
현재 사용자 결정이 이전 로컬 Notion의 취소 정책을 대체하며 팀 원문 동기화는 미확인이다.

### 2026-09-30 Workspace 정책 변경

사용자가 전달한 2026-09-30 팀 결정으로 다음 Workspace 정책을 적용한다.
이는 로컬 Notion 내보내기 사본의 기존 생성·탈퇴 규칙을 대체한다.

- OWNER의 Workspace 생성 개수에는 제한을 두지 않는다.
- 다른 멤버가 있는 OWNER는 승계할 활성 멤버를 선택한 뒤에만 탈퇴한다. OWNER 없는
  활성 Workspace를 만드는 탈퇴는 허용하지 않는다. (2026-10-05 변경: 아래 절 참조)
- 마지막 멤버가 나가면 Workspace를 논리 삭제한다.
- 생성 제한 [#396](https://github.com/woowacourse-teams/2026-Knot/issues/396)과
  [PR #406](https://github.com/woowacourse-teams/2026-Knot/pull/406)은 정책 폐기로 닫았다.
  PR은 병합하지 않았다. 후속 계약은 #397·#398·#403,
  [승계 후보 조회 #408](https://github.com/woowacourse-teams/2026-Knot/issues/408),
  [승계·탈퇴 #409](https://github.com/woowacourse-teams/2026-Knot/issues/409),
  [삭제 정책 #410](https://github.com/woowacourse-teams/2026-Knot/issues/410)에서 관리한다.

Notion 실시간 원문은 접근 실패로 동기화하지 못했다. 기존 최대 3개·OWNER 없는
Workspace 허용·마지막 멤버 탈퇴 후 유지 문구를 현재 정책으로 재사용하지 않는다.
녹음 중 삭제는 2026-09-30 담당자가 다음과 같이 선택했다. 마지막 멤버가 탈퇴해
Workspace가 삭제되는 경우, 해당 Workspace의 진행 중·일시정지 녹음은 강제로 종료하고
저장·전사·문서 생성 없이 폐기한다. 일반적인 본인 녹음 종료와 구분한다. 이 선택이 팀
Notion에 반영됐거나 팀 리뷰를 통과했다는 의미는 아니다. 다른 멤버가 남은 상태의 OWNER
삭제는 2026-10-05 정책 변경으로 없어졌다.

삭제된 Workspace의 녹음은 늦게 도착한 업로드·종료·복구 요청으로 저장하거나
다시 활성화하지 않는다. 녹음 탭에 종료를 알리는 것만으로 서버의 폐기 처리를
완료한 것으로 간주하지 않는다. 담당자는 사용자가 더 원하지 않는 데이터를 보존하기
위해 삭제를 기다리게 하는 UX를 피하려고 폐기 안을 선택했다. 기존 파일은 보존하며,
삭제 시 진행 중·일시정지 녹음본과 그 임시 오디오만 폐기한다. 기존 저장 오디오·전사·
문서의 물리 삭제·보존 기간은 변경하지 않는다. #397의 관련 미결정은 해소됐다.

### 2026-10-05 Workspace 삭제 정책 변경

담당자가 2026-10-05 다음과 같이 확정했다. 9/30 정책의 "OWNER는 승계하거나 삭제한다"를
대체한다. 결정 기록은 [ADR 410](../adr/410-workspace-deletion-only-by-last-owner-leave.md)이다.

- 다른 활성 멤버가 있는 Workspace에서 OWNER가 나가려면 반드시 승계할 멤버를 고른다.
  이 상태에서 Workspace를 삭제하는 경로는 두지 않는다.
- Workspace 논리 삭제는 OWNER 혼자 남은 상태에서 탈퇴할 때만 일어난다.
- 별도 Workspace 삭제 API(`DELETE /api/v1/workspaces/{workspaceId}`)는 만들지 않는다.
  삭제 API 단위 #470과 PR #471은 이 결정으로 닫았다.
- 이 정책을 바꾸려면 새 Issue와 ADR로 다시 결정한다. 기획·구현·리뷰에서 다른 멤버가 남은
  Workspace의 삭제 경로를 추가하지 않는다.

이전 V2의 공동 녹음·동시 편집·다중 세션 화면이 남아 있어도 현재 범위로 되돌리지 않는다.
Member당 1개라는 규칙만으로 Workspace 전체 상한을 추론하지 않는다. 최종 ERD는
Workspace 전체 상한이 없다고 적지만, 도메인 규칙은 A2 경고를 남겨 두었다. 동시에 다른
멤버가 녹음할 수 있는지와 전체 상한은 저장소 작업에서 별도 결정을 받기 전까지 충돌로
취급한다.

### 인증·로그인 정합 상태

`도메인 규칙 및 UseCase`는 GitHub OAuth, GitHub 계정당 Member 하나, 닉네임 입력 뒤 가입 완료,
닉네임 규칙, 기본 GitHub 프로필 이미지와 여러 Workspace 참여를 현재 도메인으로 적는다.
같은 도메인의 `아직 정하지 않은 것` 토글은 OAuth 세션·토큰 갱신·만료와 가입 중단 후
재진입을 미정으로 둔다. access 1시간, refresh idle 7일·absolute 30일, 회전·재사용 시
현재 로그인 계열 폐기와 현재 계열 로그아웃은 별도 API 명세와 9/30 candidate에 적혀 있지만,
이를 도메인 합의로 취급하지 않는다. 9/30 변경 로그에는 로그인 결정 항목이 없다. 이 문서 간
충돌은 남아 있다. 이 스레드에 제공된 도메인 발췌의
중복 요청 멱등성·닉네임 중복/변경 미정 항목은 현재 열린 Notion 미정 페이지에서 확인되지
않아 출처 차이로 기록한다.

2026-09-30 capture에는 GitHub OAuth callback, 닉네임 설정, refresh, logout API 후보가 있다.
네 후보는 검토 시작 시 모두 `pending`이었다. 10/1 열린 [#427](https://github.com/woowacourse-teams/2026-Knot/issues/427),
[#428](https://github.com/woowacourse-teams/2026-Knot/issues/428),
[#429](https://github.com/woowacourse-teams/2026-Knot/issues/429),
[#430](https://github.com/woowacourse-teams/2026-Knot/issues/430)은 사용자가 확인한 로그인 세션,
로그아웃, 닉네임 가입 완료, refresh 작업 범위를 기록한다. 이 Issue들은 팀 리뷰 승인이나
Notion 원문 정합 완료를 뜻하지 않는다. refresh API 본문은 204, CSRF, 7일·30일 만료, 회전,
재사용 시 family 폐기, JWT 원문 대신 hash/식별자 저장을 제안한다. 10/1 직접 본 refresh
API 페이지는 9/30 source/pending snapshot과 응답 예시·403 설명·추가 회원 수명 규칙이 다르다.
따라서 최신 캡처로 다시 맞추기 전에는 candidate 상태를 확정하지 않는다. OAuth candidate에만
있는 탈퇴 Member 재로그인 제한도 미정이다. Figma ERR-07은 로그인이 만료되면 로그인 화면으로 이동하고
“로그인이 만료됐어요. 다시 로그인해 주세요.” 주의 토스트를 표시한다고 적는다.
후보 흐름과 현재 코드의 차이는
[백엔드 로그인·API 정합 메모](../../backend/docs/notion-api-alignment.md#인증로그인-2026-09-30-후보)에,
저장·동시성 제안과 미정 결정은
[Persona 로그인 세션 draft](../../backend/.persona/decisions/draft/refresh-token-session-lifecycle.md)에
기록했다. 로그인 Issue에 적힌 사용자 결정은 이번 기획 대조의 현재 지침으로 쓰되, 팀 승인과

### 프로토타입 검증에서 남긴 연구 신호

2026-09-30 capture의 인터뷰 자료는 팀 결정이 아니라 연구 근거로 취급한다. 8월 개인 12명과

부담, 녹음→전사→AI→노션 수작업, 긴 문서의 낮은 가독성, 최신 결정 혼선이 반복됐다.
9/29 이후에는 실제 팀으로 P0 녹음 습관, P1 정리 수고, P2 주제별 찾기, P3 읽기 부담을
검증한다. 이는 진행 중인 검증 계획이지 통과 결과나 팀 승인 요구사항이 아니다.

CareerForm 인터뷰에는 문서가 지나치게 잘게 나뉘면 복잡해지고 상위 도메인·트리 구조가
필요할 수 있다는 의견, 원문 전체 복사·문서 탭·문서/요약/녹음 이력 통합 요청이 있다.
Harudeul 메모에는 Codex CLI 연결과 기기 소음의 불편이 있다. Rilog·DFGG·외부팀 템플릿에는
완료된 답변이 없어 추가 제품 신호를 만들지 않는다. 상위 `인터뷰` 페이지에는 하위 DB가
있지만 해당 child record가 source snapshot에 빠져 있어 이 부모 후보는 미완료로 둔다.
개별 인터뷰 내용은 복제하지 않고, 이 요약도 현재 V2 정책이나 팀 승인으로 보지 않는다.

### #374 구현 중 확인한 담당자 결정과 후속 Issue

다음은 2026-09-29 #374 작업 대화에서 확인한 녹음 담당자의 지시다.
팀 Notion에 반영됐거나 팀 리뷰가 승인했다는 의미는 아니다.

- 연결 끊김은 이전 대화의 30초 heartbeat·2분 유예를 확정 기준으로 옮기지 않고,
  원문의 즉시 종료와의 충돌을 남겨 녹음 구현 전에 확정한다.
- 같은 멤버의 다른 탭·기기는 상태와 경과 시간을 보고 종료할 수 있다.
  새 녹음은 막고, 오디오 수집과 일시정지는 처음 녹음을 시작한 탭이 맡는다.
  이는 다른 멤버의 공동 녹음 참여와 별개다.
- 녹음 탭을 새로고침·닫을 때 브라우저 기본 나가기 확인을 거쳐 나가면 종료 신호를
  보내고 거기까지 문서로 정리한다. 다시 들어오면 문서 정리 중 상태이며 이어 녹음은
  이후 버전이다. 종료 신호가 전달되지 않은 경우의 처리 시점은 연결 끊김 결정과 함께 확인한다.

이 결정의 후속 녹음 Issue를 등록하면 해당 링크와 원문 동기화 상태를 갱신한다.

이후 2026-10-01 기준 #384/#385는 30초 heartbeat와 2분 만료를 구현 작업으로 명시하고,
#386은 무신호 2분 뒤 수집 중단을 후속 상태 전달 계약에 포함했다. 이 열린 Issue들의 최신
범위를 추적하되, Notion·ERD 문구나 구현이 동기화됐다고 간주하지 않는다.

### #378 구현에서 적용하는 후속 녹음 계약

2026-10-01 확인한 [녹음 시작 Issue #378](https://github.com/woowacourse-teams/2026-Knot/issues/378)과
담당자 인터뷰 결과가 위 #374 당시의 새로고침 종료 정책을 대체한다.
최초 탭은 같은 세션을 자동 복구하고 일시정지 상태를 유지한다. 오디오 수집 공백은 허용한다.
최초 탭의 신호 간격은 30초, 2분 무응답이면 종료한다. 명시적 종료는 즉시 처리하며,
닫기와 새로고침 구분·이탈 신호 실패는 유예 만료로 회수한다.

[시작 API 구현 계약](../api/recording-start.md)은 멱등 키와 탭 증명을 구체화한다.
종료·복구·만료·오디오 후속 처리는 #381·#384·#385 등 후속 Issue에서 완성한다.
9월 30일 로컬 사본은 청크 대신 최종 파일 업로드와 `200 ENDED`인 세션 종료를 사용한다.
세션 종료만으로 문서 처리 중 상태를 반환하지 않는다. 팀 Notion 실시간 동기화는 미확인이다.

일반 탈퇴·OWNER 승계 탈퇴는 즉시 처리하고 본인의 진행 중·일시정지 녹음을 저장 없이 폐기한다.
다른 멤버 녹음과 이미 정상 종료·저장된 자료는 보존한다.
마지막 멤버(혼자 남은 OWNER) 탈퇴로 Workspace가 삭제되면 해당 Workspace의 진행 중 녹음을 모두 폐기한다.
권한 변경과 폐기 의도는 한 DB 트랜잭션으로 처리하고, 외부 임시 객체 정리는 커밋 뒤 재시도한다.
이는 #381·#386·#397·#409·#410의 담당자 확정 계약이며 #378의 구현 완료 범위는 아니다.

## 계속 적용할 기존 규칙

V2 전환은 모든 기술 규칙과 ADR의 일괄 폐기가 아니다.

- [기여 가이드](../../CONTRIBUTING.md), [GitHub 컨벤션](../../.github/knot-conventions.yml),
  기존 Issue·PR 템플릿과 [Issue·ADR 하네스](../harness/issue-planning.md)는 계속 적용한다.
- 인증·초대·워크스페이스 계약은 관련 [ADR 목록](../adr/README.md), 연결 Issue,
  실제 API·테스트를 확인한다. 새 기획에 없다는 이유만으로 기존 계약을 제거하지 않는다.
  명시적 충돌이 발견되면 영향과 대체 결정을 해당 작업에서 다룬다.
- 백엔드의 팀 컨벤션은 [백엔드 컨벤션 원문][백엔드]의 00~08 개별 문서를 읽는다.
  V2 제품 범위와 언어·계층·테스트·API 작성 규칙은 별도로 판정한다.
- 과거 Notion 수집·검색 ADR은 당시 결정의 이력으로 보존한다. V2 요구사항으로
  자동 재사용하지 않는다. 실제 설계를 대체할 때 [ADR 생명주기](../adr/README.md)에
  따라 새 결정과 대체 관계를 남긴다.

## 변경 시 갱신

정책을 바꾸는 작업에서는 원문의 해당 항목과 변경 로그를 먼저 확인하고,
이 문서의 관련 범위·충돌 상태·확인 날짜·출처를 함께 갱신한다.
결정 전 제안은 미정으로 남기고, 해소했다면 결정한 Issue 또는 PR을 연결한다.
원문 동기화가 남아 있으면 대상 문서와 남은 차이를 표시한다.

AGENTS에는 이 문서로 향하는 진입점만 유지한다. 개인 로컬 스킬의 출처 우선순위와
위키 라우팅 보완은 #374 저장소 PR 밖의 후속 작업이며, 개인 스킬을 저장소에 복사하지 않는다.
제품 코드, 하네스 판정 로직, 기존 ADR 전체 개편은 이 문서 정리의 범위가 아니다.
