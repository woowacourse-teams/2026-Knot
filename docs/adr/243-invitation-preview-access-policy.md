# 초대 미리보기는 하나의 공개 경로에서 코드와 링크 토큰을 함께 처리한다

## 상태

Proposed

## 관련 Issue

- #243 [BE] 초대 토큰·코드로 참여 대상 워크스페이스 조회 API 구현

## 한 줄 요약

초대 미리보기는 `GET /invitations/{tokenOrCode}` 하나로 제공하고, 6자리 코드는 대소문자 무관 조회와 주소별 JVM 호출 제한을 적용하며 링크 토큰은 원문 그대로 조회한다.

## 왜 이 결정이 필요했나

초대 수신자는 실제 참여 전에 대상 워크스페이스를 확인해야 한다. 동시에 짧은 코드는 사용자가 직접 입력하기 쉽지만 무차별 대입 위험이 있고, 링크 토큰은 길고 충분히 예측하기 어려우므로 코드와 같은 제한을 적용할 필요가 낮다.

프론트엔드는 초대 공유 UI에서 6글자 코드를 기준으로 설계하고 있었다. 사용자는 MVP에서는 단순한 Discord 방식이 적절하다고 판단했고, 대부분의 인증·코드 입력이 대문자 방식으로 처리되는지 확인한 뒤 대문자 정규화를 수용했다.

결정 동인:

- 사용자가 링크와 코드를 같은 초대 화면에서 자연스럽게 확인할 수 있어야 한다.
- 수동 입력용 코드는 짧아야 하므로 brute force 방어가 필요하다.
- MVP에서는 서버 재시작 후에도 유지되는 분산 limiter나 영속 실패 횟수보다 간단한 정책이 적합하다.
- 링크 토큰은 대소문자까지 포함한 원문 자체가 credential이므로 정규화하지 않는다.

## 트레이드 오프

| 선택지 | 장점 | 단점 | 채택 여부 |
| --- | --- | --- | --- |
| 코드와 링크 토큰을 별도 URL로 분리 | 입력 종류별 정책이 URL에 드러난다. | FE가 두 경로를 분기해야 하고 초대 credential 개념이 API에 중복된다. | 미채택 |
| 코드와 링크 토큰을 하나의 URL에서 처리 | 초대 미리보기 진입점이 단순하고 FE 계약이 작다. | 서버가 입력 길이와 형식으로 credential 종류를 분류해야 한다. | 채택 |
| 4자리 코드 | 입력이 가장 쉽다. | 경우의 수가 작아 MVP에서도 호출 제한 부담이 커진다. | 미채택 |
| 6자리 코드 | FE 시안과 맞고 수동 입력성과 탐색 비용의 균형이 맞다. | 8자리보다 경우의 수가 작아 코드 요청 제한이 필요하다. | 채택 |
| 8자리 코드 | 경우의 수가 크다. | FE 시안과 다르고 수동 입력 부담이 커진다. | 미채택 |

## 무엇을 결정했나

- 초대 미리보기는 인증 없이 호출 가능한 `GET /invitations/{tokenOrCode}`로 제공한다.
- 입력을 `strip()`한 뒤 길이가 6이면 초대 코드 후보로 본다.
- 초대 코드는 `Locale.ROOT` 기준 대문자로 정규화하고, 혼동 문자를 제외한 알파벳 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`만 허용한다.
- 그 외 nonblank 입력은 링크 토큰으로 보고 원문 그대로, 대소문자를 구분해 조회한다.
- 코드 후보 조회만 remote address별 JVM local fixed-window limiter를 적용한다.
- fixed window는 첫 코드 요청 시각부터 1분이며, 30회까지 허용하고 31번째부터 `429`와 `Retry-After`를 반환한다.
- JVM limiter는 주소 카운터를 최대 10,000개만 보관하고, 한도를 넘은 새 주소는 공유 overflow 창으로 묶어 메모리 증가를 제한한다.
- 미리보기 실패 원인은 외부 응답에서 구분하지 않고 같은 `404`로 응답한다.

## 결과

- 공개 미리보기는 초대를 소비하지 않고 workspace ID와 이름만 반환한다.
- V3 초대 row도 lookup hash와 유효 상태가 맞으면 복호화 없이 미리보기할 수 있다.
- 링크 토큰 조회는 호출 제한을 소비하지 않는다.
- 코드 조회 제한은 JVM 메모리에만 남으므로 서버 재시작이나 다중 인스턴스 환경에서는 전역 제한을 보장하지 않는다.
- 추적 주소가 한도에 도달하면 새 주소들은 overflow 카운터를 공유하므로 정상 요청도 일시적으로 제한될 수 있다.

## 다시 논의해야 할 조건

- 운영에서 다중 인스턴스 배포를 시작해 주소별 전역 rate limit이 필요해질 때
- 초대 코드 길이 또는 알파벳을 FE 입력 UX와 다르게 바꿔야 할 때
- 링크 토큰에도 abuse 방어가 필요하다는 운영 증거가 생길 때
- 참여 API에서 실패 횟수, 차단, 감사 이력을 영속해야 할 때
