# 최초 탭은 새로고침 시 제어를 복구하고 다른 탭은 조회·종료만 허용하며 무응답은 2분 뒤 종료한다

## 상태

Proposed

## 관련 Issue

- #378 [BE] 녹음 시작 API 구현

## 한 줄 요약

최초 탭은 새로고침 시 제어를 복구하고 다른 탭은 조회·종료만 허용하며 무응답은 2분 뒤 종료한다

## 왜 이 결정이 필요했나

최초 탭만 녹음을 제어하며 Member당 활성 세션은 Workspace와 무관하게 하나다

브라우저 이탈 신호는 전달과 닫기·새로고침 구분을 보장하지 않는다

결정 동인:

- 같은 탭의 새로고침은 같은 세션을 자동 복구해야 한다
- 다른 탭·기기 제어 인계 방지
- 브라우저 이탈 신호 유실 허용

## 트레이드 오프

- 이전 안: 새로고침·닫기 모두 종료. 이탈 처리가 단순하지만 새로고침 자동 복구 요구를 충족하지 못한다
- 채택안: 같은 탭 새로고침 자동 복구, 닫기 감지 실패는 2분 무응답 만료. 수집 공백과 닫기 종료 지연을 감수한다

## 무엇을 결정했나

최초 탭은 새로고침 시 제어를 복구하고 다른 탭은 조회·종료만 허용하며 무응답은 2분 뒤 종료한다

기존 녹음 담당자 인터뷰의 자동 복구 요구를 따른다. 최초 탭 증명을 유지하고 종료된 세션은 재활성화하지 않는다

### 시작 요청의 재시도와 제어 증명

응답 유실로 프론트가 같은 시작 요청을 두 번 보내도 녹음은 하나만 생성한다.
`requestId`는 시작 작업을 식별하고, `tabId`는 최초 탭을 식별하며,
`controlToken`은 최초 시작 때 만든 비밀값을 알고 있음을 증명한다.
서버가 생성한 `recordingId`는 저장된 녹음의 식별자다.

다음 판정은 인증과 현재 Workspace 접근 권한 검증을 통과한 같은 회원의 요청에 적용한다.

| 요청 조건 | 서버 처리 |
| --- | --- |
| 기존 `requestId`이며 Workspace·`tabId`·토큰 해시 모두 일치 | 기존 녹음의 현재 상태를 `200`으로 반환 |
| 기존 `requestId`인데 Workspace·`tabId`·토큰 중 하나라도 불일치 | 최초 요청과 다른 입력이므로 `409`. 기존 녹음이 종료됐어도 동일 |
| 새 `requestId`인데 회원의 RECORDING 또는 PAUSED가 존재 | 활성 녹음 중복 시작이므로 `409` |
| 새 `requestId`이며 회원의 활성 녹음이 없음 | 새 녹음을 생성하고 `201` 반환 |

동일 요청이 동시에 도착해도 잠금과 DB 제약으로 녹음 하나와 `201`·`200`으로 수렴한다.
재시도는 상태·시작 시각·생존 시각을 변경하지 않는다. ENDED도 그대로 반환하며 재활성화하지 않는다.

프론트는 첫 전송 전에 `requestId`·`tabId`·`controlToken`을 준비하고 보관한다.
토큰은 암호학적으로 안전한 32바이트 난수를 패딩 없는 Base64URL로 인코딩한다.
재시도와 같은 탭 새로고침에는 기존 값을 사용하고, 진행·일시정지 중에는 토큰을 유지한다.
녹음 종료 후 새 녹음을 시작할 때 `requestId`와 토큰을 새로 생성한다. 같은 탭의 `tabId`는 유지할 수 있다.

프론트가 재시도를 전송하고 백엔드는 중복 생성을 방지한다.
백엔드는 원문 토큰 대신 SHA-256 해시만 저장하며 토큰 자체의 만료 시간은 두지 않는다.
이는 세션의 무응답 만료와 별개다. 세 값을 복제한 요청은 서버에서 원래 요청과 구분할 수 없으므로
물리적인 브라우저 탭을 인증하는 보장은 아니다.

재시도 대상 오류·횟수·간격, 브라우저 보관 방식·다른 탭 복제 방지·삭제 시점은
FE 연동에서 결정할 항목이다. 현재 FE 생성·보관·재시도와 실제 마이크 복구는 미구현·미검증이다.
서버 세션 복구가 새로고침 중 오디오의 연속 수집을 보장하지 않는다.

## 결과

- 녹음 상태는 새로고침 전 RECORDING 또는 PAUSED를 유지한다
- 최초 탭이 요청 키·탭 식별자·제어 증명을 유지해야 한다
- 오디오 수집 공백과 닫기 종료 지연을 허용한다
- 종료·복구·만료 HTTP 및 FE 연동은 후속 Issue에서 완성한다
