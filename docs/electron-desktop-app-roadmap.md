## 0. 이 문서의 지위

### 0.1 무엇의 정본인가

| 이 문서가 정본인 것 | 이 문서가 정본이 아닌 것 (정본 위치) |
| --- | --- |
| 작업 목록·ID·순서·의존 관계 | 사실(코드·외부 문서 값) → [지식 문서](./electron-desktop-app-knowledge.md), [패키징 부록](./electron-desktop-app-packaging-research.md) |
| 각 작업의 현재 상태와 완료 판정 | 설계·대안·근거 → [기술 기획서](./electron-desktop-app-tech-plan.md) |
| 게이트(다음 단계로 넘어갈 조건) | 적용 가능성 판정 → [검토 문서](./llm-electron-subscription-architecture-review.md) |

**충돌 시 우선순위**: 확정 ADR(`Accepted`) > 이 문서(실행 상태·순서) > 기술 기획서(설계 초안) > 나머지 조사 문서.
설계 내용이 ADR로 확정되면 기획서를 갱신하고, 이 문서는 링크만 유지한다. **설계 본문을 이 문서로 복사하지 않는다.** 복사는 SSOT를 깨뜨린다.

### 0.2 문서 우선 원칙 (가장 중요)

**코드보다 문서가 먼저다. 코드와 문서가 어긋나면 문서가 맞다.**

- 코드를 먼저 고치지 않는다. 계획·계약·설계가 바뀌면 이 문서와 기획서를 먼저 고치고, 코드를 그 문서에 맞춘다.
- 구현 중 문서와 다른 사실을 발견하면 **그 자리에서 멈춘다.** 코드를 근거로 문서를 되돌리지 않는다. 문서를 정정해 확정한 뒤 코드를 맞춘다.
- 문서가 실제와 다르다고 판단되면 코드를 따라가지 말고 어긋난 지점·영향·정정안을 사람에게 보고한다. 판단만으로 문서를 바꾸지 않는다.
- 지식 문서처럼 관찰한 사실을 적은 문서는 **실제 값으로 정정하는 것**이 "문서를 먼저 고치는 것"이다. 정정 날짜와 근거(경로:라인 또는 URL)를 함께 남긴다.
- 문서에 없는 것을 임의로 구현하지 않는다. 필요하면 먼저 작업 행을 추가하거나 5절 결정 대기로 올린다.

### 0.3 갱신 규칙

- 상태 변경은 **그 변경을 만든 PR에서 같이 커밋**한다. 별도 "문서 갱신 PR"을 만들지 않는다.
- 작업 ID(`A1`, `B1` …)는 **영구 불변**이다. 폐기해도 행을 지우지 않고 상태를 `폐기`로 바꾸고 사유를 남긴다.
- Issue 번호·ADR 파일명은 실제로 생성된 뒤에만 채운다. `{ISSUE_NUMBER}` 같은 표시는 이 문서에 쓰지 않는다.
- 새 작업을 추가할 때는 반드시 선행·완료 판정·위험 신호를 함께 적는다. 셋 중 하나라도 못 쓰면 그 작업은 아직 작업이 아니라 미결 결정(5절)이다.
- 이 문서는 **Issue를 자동으로 만들지 않으며 원격 쓰기 권한이 아니다.** Issue 생성은 매번 사용자가 현재 요청에서 명시하고 판정기가 `pass`·`publish_ready=true`일 때만 한다.

## 1. 한 줄 목표

> Knot 데스크톱 앱은 `https://knoted.kr` 웹 앱을 원격 로드하는 Electron 셸이다. 채팅·검색·LLM 호출·답변 저장은 기존 Spring 백엔드 계약을 그대로 쓴다. 데스크톱이 더하는 것은 상시 실행·딥링크·알림·퀵 질문 창·자동 업데이트다.

트랙은 둘이며 **서로 독립**이다. 하나가 막혀도 다른 하나는 진행한다.

| 트랙 | 내용 | 왜 분리하나 |
| --- | --- | --- |
| **A. 데스크톱 셸** | Electron 셸·빌드·서명·배포·인증·딥링크 | 제품 요구가 확정돼야 시작 |
| **B. 채팅 모델 어댑터** | 백엔드 `LlmClient`에 Anthropic 어댑터 추가 | "채팅을 Claude로" 목적은 Electron과 무관하게 달성 가능(검토 문서 7절 권고) |

### 2.1 지금 착수 가능한 작업

다음에 무엇을 구현할지는 여기서 고른다. 위에서부터 처음 만족하는 규칙을 따른다.

1. 상태가 `구현중` 또는 `검증중`인 작업이 있으면 **그것을 먼저 끝낸다.** 새 작업을 열지 않는다.
2. 없으면 아래 목록에서 순위가 높은 것을 고른다. 이 목록에는 상태가 `준비됨`이고 선행 작업·미결 결정·게이트가 모두 풀린 작업만 올린다.
3. 목록이 비어 있으면 **새 작업을 시작하지 않는다.** 무엇이 막고 있는지(3절 게이트 또는 5절 결정 대기)를 사람에게 보고하고 답을 기다린다.

| 순위 | ID | 작업 | 왜 지금 가능한가 |
| --- | --- | --- | --- |
| 1 | B0 | 채팅·임베딩 provider 설정 분리 | 선행·게이트 없음. B1의 필수 선행이라 가장 먼저 풀어야 함 |
| 2 | W1 | 웹 로그아웃 액션 + `useDesktop` 감지 훅 | 선행·게이트 없음. 현재 SPA에 로그아웃 호출 코드가 없어 데스크톱과 무관하게 필요 |
| 3 | W3 | 웹 CSP 헤더(Cloudflare `_headers`) | 선행·게이트 없음. U15 실측을 겸함 |

트랙 A(`A1~A13`)는 **전부 G0 게이트에 막혀 있다.** G0이 통과되기 전에는 `desktop/` 디렉터리를 만들거나 Electron 의존성을 추가하지 않는다.

이 목록은 4절 표에서 파생된다. 둘이 어긋나면 4절이 정본이며 이 목록을 즉시 고친다. 작업 상태를 바꿀 때 이 목록도 같은 PR에서 갱신한다.

## 3. 게이트

게이트는 **사람이 명시적으로 통과 선언**해야 넘어간다. 통과 시 이 절의 체크박스를 채우고 날짜·근거를 적는다.

### G0 — 제품 결정 게이트 (트랙 A 착수 전, 현재 위치)

검토 문서는 데스크톱 앱을 "대규모 신규 개발"로 판정했다. 코드를 쓰기 전에 팀이 만들기로 합의해야 한다.

- [ ] 팀이 데스크톱 앱을 만들기로 합의했다 (합의 날짜·기록 위치: )
- [ ] 데스크톱이 주는 값(상시 실행·딥링크·알림·퀵 질문)이 실제 사용자 요구로 확인됐다
- [ ] Q1(macOS 서명 계정)과 Q2(Windows 서명)의 비용을 팀이 수용했다 → 5절
- [ ] Q4(`desktop/` 위치·브랜치 area)가 정해졌다 → 5절

**G0 미통과 상태에서 할 수 있는 것**: 트랙 B 전체(`B0`~`B3`)와 웹 선행 작업(`W1`~`W3`). 4.2절 참조.

- [ ] Electron 창에서 GitHub 로그인이 경고·차단 없이 끝까지 동작한다 (U1 해소)

## 7. 불변 계약 (위반하면 작업을 멈춘다)

이 목록을 바꾸려면 이 문서와 관련 ADR을 함께 고쳐야 한다. PR 리뷰에서 이 절을 확인한다.

1. **백엔드 채팅 계약 무변경**: SSE `chunk`/`complete`/`error`, 문서 준비 게이트(`CHAT_DOCUMENTS_NOT_READY`), 답변·출처 저장, 세션당 스트림 1개, 30초 타임아웃. `chat/` 패키지 diff는 LLM 어댑터를 제외하고 0이어야 한다.
2. **클라이언트에서 LLM을 호출하지 않는다.** 답변·출처를 클라이언트가 저장하지 않는다. 데스크톱 전용 채팅 경로를 만들지 않는다.
3. **사용자 개인 Claude 구독으로 모델을 호출하지 않는다.** 검토 문서 8절 전제 조건(서면 사전 승인 포함)이 모두 충족되기 전까지 금지.
4. **Electron 보안 체크리스트 20항목 + 권장 Fuses**(기획서 8절)를 낮추지 않는다. `nodeIntegration`·`contextIsolation`·`sandbox`·네비게이션 허용 목록·IPC sender 검증은 협상 대상이 아니다.
5. **preload는 기획서 4.4 인터페이스만 노출한다.** `ipcRenderer` 원본 노출 금지.
6. **웹 사용자에게 회귀를 만들지 않는다.** 웹 배포 워크플로우·E2E 무변경 통과가 모든 M1 작업의 완료 조건이다.
7. **공통 Issue 계약을 우회하지 않는다.** 고위험 신호가 있으면 인터뷰 → Grill → ADR. Issue 본문은 `구현 기능 설명`·`TODO`·`메모` 3섹션만. 계약 전문·ADR 전문·인터뷰 원문은 Issue에 넣지 않는다.
8. **원격 쓰기는 요청마다 별도 승인**이다. Issue 생성·commit·push·PR·merge 권한은 각각 따로 판정한다.
9. **문서를 코드에 맞추지 않는다.** 0.2절 문서 우선 원칙을 어긴 PR은 병합하지 않는다. 코드가 문서와 다르면 코드가 틀린 것이다.

## 10. 작업 1건 실행 절차 (매번 반복)

0. **문서를 먼저 읽는다.** 이 문서 → 필요한 범위의 기획서 절 → 관련 ADR 순. 코드부터 열지 않는다.
1. 2.1절에서 작업 ID를 고른다. 선행·미결·게이트가 안 풀렸으면 3절·5절로 가서 사람에게 보고한다.
2. `/knot-issue-planning`으로 Issue를 기획한다. 고위험 신호가 있으면 `/knot-deep-interview` → `/knot-grill-me`.
3. 판정기가 `pass`·`publish_ready=true`이고 **사용자가 현재 요청에서 Issue 생성을 명시**했을 때만 `--publish`한다.
4. 이 문서의 해당 행에 Issue 번호를 적고 상태를 `구현중`으로 바꾼다.
5. 구현 브랜치에서 작업한다. `adr.required=true`면 실제 Issue 번호로 `harness/materialize_adr.py`를 실행해 `Proposed` ADR을 같은 PR에 포함한다.
6. 구현 중 문서와 다른 사실을 발견하면 코드를 진행하지 말고 0.2절에 따라 문서를 먼저 정정한다.
7. PR 전에 7절 불변 계약과 (데스크톱이면) 기획서 8절 보안 체크리스트를 확인한다.
8. 병합 후 이 문서의 상태를 `완료`로 바꾸고, 실측으로 해소된 U·R 항목을 갱신한다. 게이트 조건을 채웠으면 3절 체크박스도 함께 채운다.
