# 코드 리뷰 커맨드

이 커맨드는 **현재 피처 브랜치와 `develop` 브랜치의 변경사항**을 비교하여, 변경된 코드 전체에 대한 리뷰 리스트를 작성함.

**변경 파일 하나당 에이전트 하나를 병렬로 띄워** 리뷰 속도를 확보하고, 파일 단위로는 잡히지 않는 문제를 별도 패스에서 교차 검토함.

작성 결과물은 레포 내부가 아니라 **OS 임시 디렉토리**에 저장하고, 작성이 끝나면 **VS Code로 자동으로 열어줌.**

## `code-reviewer` 에이전트와의 역할 구분

두 도구는 **판정 기준(`checklist.md`)만 공유하고, 역할은 서로 침범하지 않음.**

| | 시점 | 대상 | 출력 |
| --- | --- | --- | --- |
| `code-reviewer` 에이전트 | 코드 작성·수정 직후 | 워킹 트리 (`git diff`) | 터미널, 짧게 |
| **`/review` (이 커맨드)** | **PR 올리기 전** | **`develop...HEAD` 브랜치 전체** | **md 파일 + VS Code** |

- 이 커맨드는 `code-reviewer` 에이전트를 호출하지 않음. **자체 프롬프트로 파일별 리뷰 에이전트를 띄움.** (3단계 참고)
- 심각도·판정 기준은 양쪽 모두 `checklist.md`를 따르므로 결과가 갈리지 않음.

## 이 커맨드가 하는 일

1. **변경사항 확인** - `develop` 대비 무엇이 바뀌었는지 정확히 파악
2. **체크리스트 로드** - 리뷰 기준과 근거 규칙을 로드
3. **파일별 리뷰 (병렬)** - 변경 파일마다 에이전트 하나를 띄워 동시에 리뷰
4. **교차 파일 검토** - 파일 단위로는 잡히지 않는 항목을 메인이 직접 확인
5. **취합 및 문서 작성** - 결과를 하나의 md로 정리하여 임시 파일에 작성
6. **VS Code로 열기** - 작성된 파일을 자동으로 오픈

## 1단계: 변경사항 확인

아래를 **모두** 수행하여 변경사항을 명확하고 정확하게 파악.

```bash
git branch --show-current                          # 현재 브랜치 확인
git merge-base develop HEAD                        # 분기 지점 확인
git log develop..HEAD --oneline                    # 쌓인 커밋 목록
git diff develop...HEAD --stat                     # 변경 파일 개괄
git diff develop...HEAD --name-status              # 파일별 변경 유형 (A/M/D/R)
git status --short                                 # 커밋되지 않은 변경사항
```

- **반드시 3점 diff(`develop...HEAD`)를 사용.** 2점 diff(`develop..HEAD`)는 develop에 새로 들어온 커밋까지 섞여 들어와 리뷰 대상이 오염됨.
- 커밋되지 않은 워킹 트리 변경사항이 있으면 사용자에게 **리뷰 대상에 포함할지 질문**하고, 답변에 따라 기준을 `develop...HEAD` 또는 `develop`으로 정함. **이후 모든 단계에서 동일한 기준을 사용.**
- 현재 브랜치가 `develop`이면 리뷰할 대상이 없으므로 **작업을 멈추고 사용자에게 알림.**
- `develop` 브랜치가 로컬에 없거나 뒤처져 있으면, `git fetch origin develop` 후 `origin/develop` 기준으로 비교할지 사용자에게 확인.

## 3단계: 파일별 리뷰 (병렬 실행)

### 3-1. 리뷰 대상 선정

`git diff <기준> --name-status`의 결과에서 아래를 **제외**하고 대상 목록을 만듦.

- 삭제된 파일 (`D`) — 삭제 자체의 타당성은 4단계 교차 검토에서 확인
- 잠금 파일·빌드 산출물 — `pnpm-lock.yaml`, `dist/`, `node_modules/`
- 이름만 바뀐 파일(`R`) 중 내용 변경이 없는 것 — 위치 타당성은 4단계에서 확인

대상 파일이 **2개 이하면 병렬화하지 않고 메인이 직접 리뷰.** 에이전트 기동 비용이 더 큼.

대상 파일이 **20개를 초과하면** 사용자에게 알리고 진행 여부를 확인.

### 3-2. 에이전트 병렬 실행

**대상 파일 하나당 에이전트 하나**를 띄움.

- **[매우 중요]** 여러 에이전트를 **하나의 메시지에서 동시에 호출**해야 병렬로 실행됨. 한 번에 하나씩 호출하면 순차 실행되어 의미가 없음.
- 한 번에 최대 **10개**씩 묶어 호출하고, 대상이 더 많으면 다음 묶음을 이어서 호출.
- `subagent_type`은 `general-purpose`를 사용.
- `description`은 `리뷰: <파일명>` 형태로 짧게.

각 에이전트에게 **아래 프롬프트를 파일 경로와 비교 기준만 바꿔서** 전달.

````
## 반드시 지킬 것

- **코드를 절대 수정하지 마십시오.** 리뷰만 수행합니다.
- 각 지적은 **체크리스트 항목 번호**를 반드시 포함합니다. 번호를 붙일 수 없으면 지적하지 않습니다.
- 각 지적은 **diff·근거·개선 방향** 세 가지를 모두 포함합니다. 하나라도 없으면 항목으로 만들지 않습니다.
- 근거는 "안 좋습니다" 수준이 아니라 **어떤 상황에서 무엇이 실제로 잘못되는지**를 구체적으로 서술합니다.
- 개선 방향에는 **개선 코드 블록**을 함께 제시합니다. 파일 전체를 다시 쓰지 말고 바뀌는 부분만 발췌합니다.
- 체크리스트의 **"알려진 예외"** 표에 해당하는 사항은 지적하지 않습니다. (테스트 러너 미도입, `src/pages` 하위 kebab-case, Tailwind 미사용, `src/modules` 부재)
- 확신이 없으면 단정하지 말고 `질문`으로 분류합니다.
- 지적 개수를 채우려고 사소한 것을 부풀리지 마십시오. 지적할 것이 없으면 없다고 하십시오.
- 심각도 표기에 **이모지를 사용하지 마십시오.**
- 전 구간 **높임말**을 사용하고, 사람이 아니라 **코드를 지적**합니다.

#### [주요] E-3 — 파생 상태를 useState와 useEffect로 동기화

**해당 코드** (`<파일 경로>:42`)

```diff
+ const [isValid, setIsValid] = useState(false);
+ useEffect(() => {
+   setIsValid(name.length > 0);
+ }, [name]);
```

**왜 문제인가**

`isValid`는 `name`으로부터 즉시 계산되는 파생 값입니다. 이를 별도 상태로 두고 `useEffect`로 동기화하면 다음 문제가 생깁니다.

- `name`이 바뀐 렌더에서 `isValid`는 아직 이전 값이므로, 한 프레임 동안 화면과 상태가 어긋납니다.
- 상태 변경 → 리렌더 → `useEffect` → 상태 변경 → 리렌더로 렌더링이 두 번 발생합니다.
- `isValid`를 갱신하는 경로가 늘어날수록 동기화가 깨질 지점이 함께 늘어납니다.

**개선 방향**

렌더 중에 직접 계산하여 상태를 하나 줄입니다.

```tsx
const [name, setName] = useState("");
const isValid = name.length > 0;
```
````

## 4단계: 교차 파일 검토

**파일 하나만 봐서는 잡히지 않는 항목**을 메인이 직접 확인. 3단계 결과가 모두 도착한 뒤 수행.

| 확인 항목 | 방법 |
| --- | --- |
| C-1-2 참조 방향 역류 | 변경 파일의 임포트 구문을 모아, `pages > widgets > features > composites > primitives` 역방향 임포트가 있는지 확인 |
| C-1-3 동일 레벨 조합 | widgets↔widgets, features↔features, composites↔composites 임포트가 있는지 확인 |
| C-1-7 캐시 공유 | 같은 데이터를 widgets가 features로 props drilling 하고 있는지 확인 |
| C-1-8 도메인 중복 | 도메인이 겹쳐 컴포넌트를 재사용하고 있는지, 훅으로 내려야 하는지 확인 |
| C-2-2 세그먼트 캡슐화 | 세그먼트 내부 파일(`ui/`, `model/`, `utils/`)이 컴포넌트 폴더 밖에서 임포트되는지 Grep으로 확인 |
| C-5-1 엔드포인트 일치 | `fetch/` 폴더 경로와 실제 API 경로가 일치하는지 확인 |
| C-6-5 쿼리키 일치 | 같은 리소스의 query·suspense·prefetch가 동일한 queryKey factory와 동일한 fetch 함수를 쓰는지 확인 |
| H-6 중복 코드 | 여러 파일에 같은 로직이 3회 이상 반복되는지 확인 |
| 삭제·이동 파일 | 삭제된 파일을 참조하는 곳이 남아 있는지, 이동한 위치가 규칙에 맞는지 확인 |

- 여기서 나온 지적은 최종 문서의 **"교차 파일 검토"** 섹션에 파일별 리뷰와 동일한 형식(`[심각도] 항목번호 — 요약` + diff·근거·개선)으로 작성.
- **중복 제거**: 파일별 리뷰에 이미 같은 지적이 있으면 교차 섹션에서 빼고, 파일별 항목에 관련 파일을 덧붙임.

## 5단계: 취합 및 문서 작성

### 심각도와 판정

`checklist.md`의 정의를 그대로 사용.

| 심각도 | 기준                                                  |
| ------ | ----------------------------------------------------- |
| `치명` | 버그·데이터 손상·보안 문제. 머지 전 반드시 수정.       |
| `주요` | 프로젝트 규칙 위반, 명백한 설계 문제. 수정 권장.       |
| `제안` | 가독성·일관성 개선. 반영 여부는 작성자 판단.           |
| `질문` | 의도가 파악되지 않아 확인이 필요한 부분.               |

판정: `치명`·`주요` 없으면 **승인**, `주요`만 있으면 **주의**, `치명` 1건 이상이면 **차단**.

**심각도·판정 표기에 이모지를 사용하지 않음.** (체크리스트 `H-8`)

### 저장 위치

```bash
mkdir -p /tmp/knot-review
```

파일 경로: `/tmp/knot-review/<브랜치명을 -로 치환>-review.md`

- 예: 브랜치가 `fe/feature/#189` 이면 → `/tmp/knot-review/fe-feature-189-review.md`
- 파일이 이미 존재하면 덮어씀.
- **레포 내부(`context/` 포함)에는 절대 작성하지 않음.**

### 문서 형식

````md
# 코드 리뷰 — <브랜치명>

- **비교 대상**: `develop...HEAD`
- **변경 파일**: N개 (+추가 라인 / -삭제 라인)
- **커밋**: N개
- **판정**: 승인 | 주의 | 차단
````

### 말투 규칙

- 전 구간 **높임말** 사용. (`~합니다.`, `~입니다.`)
- 사람이 아니라 **코드를 지적.** (`~하셨습니다` ❌ → `~하도록 구현되어 있습니다` ✅)
- 단정적이되 공격적이지 않게. 근거 없는 강한 표현("끔찍합니다", "말이 안 됩니다") 금지.

## 6단계: VS Code로 열기


마지막에 사용자에게 **판정, 심각도별 항목 개수, 저장 경로**를 한두 줄로 알려줌.

## 주의사항

- **[매우 중요]** 이 스킬은 **코드를 수정하지 않음.** 리뷰 문서 작성 전용. 서브 에이전트에게도 수정을 금지시킴. 수정 요청은 사용자가 별도로 지시할 때만 수행.
- **[매우 중요]** 변경 파일을 임의로 샘플링하지 않음. 전부 확인. 에이전트가 실패한 파일은 메인이 직접 채움.
- **[매우 중요]** 여러 에이전트는 **한 메시지에서 동시에** 호출. 순차 호출하면 병렬화 이점이 사라짐.
- **[매우 중요]** 리뷰 문서는 반드시 `/tmp/knot-review/` 하위에 작성. 레포 내부에 작성 금지.
- **[매우 중요]** `checklist.md`의 "알려진 예외"를 반드시 확인하고, 해당 사항은 개별 항목으로 만들지 않음. 오탐은 리뷰 전체의 신뢰를 떨어뜨림.
- 파일별 리뷰와 교차 검토에서 **같은 지적이 중복되지 않도록** 취합 시 병합.
- 근거 없는 추측성 지적 금지. 확인이 필요하면 `질문`으로 분류.
- 변경사항이 없으면 문서를 만들지 않고 사용자에게 알림.
