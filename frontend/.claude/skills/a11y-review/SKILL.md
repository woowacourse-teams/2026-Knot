# 접근성 점검 커맨드

이 커맨드는 **현재 피처 브랜치와 `develop` 브랜치의 변경사항**에서 **접근성만** 점검함.

접근성은 기본 리뷰(`/review`, `code-reviewer`)에서 분리되어 있어, 기본 리뷰는 접근성을 지적하지 않음. 접근성을 확인하고 싶을 때 이 커맨드를 따로 실행함.

결과는 파일로 저장하지 않고 **채팅 답변으로만** 보여줌.

## `/review`와의 관계

| | 대상 | 기준 | 출력 |
| --- | --- | --- | --- |
| `/review` | 프로젝트 규칙·버그 등 (접근성 제외) | `.claude/skills/review/checklist.md` | md 파일 + VS Code |
| **`/a11y-review` (이 커맨드)** | **접근성만** | **`.claude/skills/a11y-review/checklist.md`** | **채팅 답변** |

- 이 커맨드의 결과는 `/review`의 판정(승인·주의·차단)과 합치지 않음.
- 이미 만들어 둔 동작이 깨진 경우(예: 만들어 둔 Esc 닫기가 동작하지 않음)는 `/review`가 `B` 항목으로 잡음. 이 커맨드는 접근성 기준 충족 여부만 봄.

---

## 1단계: 변경사항 확인

이 커맨드의 모든 명령은 **`frontend/` 폴더에서** 실행. 저장소 루트에서 실행하면 백엔드 변경이 섞이고, 체크리스트 경로(`.claude/skills/a11y-review/checklist.md`)도 찾지 못함.

```bash
git branch --show-current                          # 현재 브랜치 확인
git merge-base develop HEAD                        # 분기 지점 확인
git diff develop...HEAD --stat --relative          # 변경 파일 개괄
git diff develop...HEAD --name-status --relative   # 파일별 변경 유형 (A/M/D/R)
git status --short --untracked-files=all -- .      # 커밋되지 않은 변경사항 (미추적 파일 포함)
```

- **경로는 모두 `frontend/` 기준.** `git diff`는 기본으로 저장소 루트 기준 경로를, `git status`는 현재 폴더 기준 경로를 출력하므로 `--relative`와 `-- .`로 맞춤.
- **반드시 3점 diff(`develop...HEAD`)를 사용.** 2점 diff는 develop에 새로 들어온 커밋까지 섞임.
- 커밋되지 않은 변경사항이 있으면 사용자에게 **점검 대상에 포함할지 질문**하고, 답에 따라 기준을 정함. 이후 모든 단계에서 같은 기준을 사용.
  - 포함하지 않음 → `develop...HEAD`
  - 포함함 → 위에서 확인한 **분기 지점 커밋(`<merge-base>`)**. `git diff <merge-base>`는 커밋한 변경과 커밋하지 않은 변경을 함께 보여줌. `develop`을 기준으로 쓰면 develop에 새로 들어온 다른 사람의 변경이 거꾸로 섞이므로 쓰지 않음.
  - 포함할 때 `git status`의 미추적 파일(`??`)은 diff에 나오지 않으므로 **신규 파일로 취급**해 점검 대상에 넣음.
- 확정한 기준의 변경 파일(커밋되지 않은 변경을 포함하기로 한 경우에만 미추적 파일도 포함)을 모두 모은 뒤 점검할 변경이 있는지 판단. 현재 브랜치가 `develop`이거나 변경사항이 없으면 **작업을 멈추고 사용자에게 알림.**
- `develop` 브랜치가 로컬에 없거나 뒤처져 있으면, `git fetch origin develop` 후 `origin/develop` 기준으로 비교할지 사용자에게 확인. 그렇게 하기로 했다면 위 명령과 분기 지점 계산(`git merge-base origin/develop HEAD`)의 `develop`을 모두 `origin/develop`으로 바꿈.

## 2단계: 점검 대상 선정

- 변경된 `.tsx` 파일
- 키보드·포커스·`aria-*` 속성을 다루는 변경된 `.ts` 파일 (주로 `model/*.ts` 훅)
  - `.ts`만 바뀐 경우에도 그 코드를 쓰는 컴포넌트를 Grep으로 찾아 읽고, 변경으로 영향을 받는 F 항목을 확인.
- 일반 데이터 처리 `.ts`, 삭제된 파일, 테스트, 문서, 설정 파일은 제외.

## 3단계: 점검

`.claude/skills/a11y-review/checklist.md`를 **반드시 읽고**, 대상 파일마다 아래를 수행.

1. `git diff <기준> -- '<파일 경로>'`로 변경 내용 확인. 경로는 작은따옴표로 감쌈. `[workspaceId]`처럼 대괄호가 든 경로는 따옴표가 없으면 zsh에서 명령 자체가 실패함. diff가 비어 있으면 `git status --short -- '<파일 경로>'`로 상태를 확인.
   - `??`로 나오면 미추적 신규 파일이므로 파일 전체를 새로 추가된 코드로 봄.
   - 아무것도 나오지 않으면 경로가 잘못된 것이므로 `frontend/` 기준으로 고쳐 다시 확인.
2. 파일 **전체 내용**을 Read로 읽음. diff만 보고 판단하면 오탐이 발생함.
3. 사용하는 공통 컴포넌트가 이미 접근성을 처리하는지 확인. (예: `div`처럼 보이는 요소가 실제로는 `button`을 그리는 공통 컴포넌트인지)
4. F-1~F-7을 적용

- 병렬 에이전트를 띄우지 않고 **메인 세션이 직접 점검.**
- 코드만으로 확인할 수 없는 항목(예: 실제 포커스 이동 순서(F-3), 모달의 포커스 트랩 동작(F-7))은 통과로 단정하지 않고 `질문`으로 분류.
- 이번 변경과 관계없는 기존 코드의 문제는 지적하지 않음.

## 4단계: 결과 출력

아래 형식으로 **채팅에만** 작성. 파일로 저장하지 않음.

````md
## 접근성 점검 결과 — <브랜치명>

- **비교 대상**: `<1단계에서 확정한 기준>` (커밋되지 않은 변경 포함 여부)
- **점검 파일**: N개
- **개수**: 주요 N / 질문 N

### [주요] F-4 — 아이콘 전용 버튼에 접근 가능한 이름이 없음

**파일**: `src/.../index.tsx:42`

**문제**: 스크린리더가 버튼을 "버튼"으로만 읽어, 무엇을 하는 버튼인지 알 수 없습니다.

**수정**:

```tsx
<IconButton icon={<CloseIcon />} />                      // 수정 전
<IconButton icon={<CloseIcon />} aria-label="닫기" />    // 수정 후
```
````

- 지적할 것이 없으면 "접근성 기준에 걸리는 변경이 없습니다." 한 줄만 작성.
- 판정(승인·주의·차단)은 쓰지 않음. 기본 리뷰의 판정과 헷갈리지 않도록 개수만 표기.
- 전 구간 **높임말**을 사용하고, 사람이 아니라 **코드를 지적.**
- 심각도 표기에 **이모지를 사용하지 않음.**

## 주의사항

- **[매우 중요]** 이 스킬은 **코드를 수정하지 않음.** 점검 결과 출력 전용. 수정 요청은 사용자가 별도로 지시할 때만 수행.
- **[매우 중요]** 결과를 파일로 저장하지 않음. 채팅 답변으로만 보여줌.
- 근거 없는 추측성 지적 금지. 확인이 필요하면 `질문`으로 분류.
- 지적 개수를 채우려고 사소한 것을 부풀리지 않음.
